## Задача 1. API Gateway

### Сравнение решений

Сравниваются Kong Gateway OSS, NGINX Open Source и Traefik Proxy. Возможности коммерческих редакций не считаются.

| Критерий | Kong Gateway OSS | NGINX Open Source | Traefik Proxy |
|---|---|---|---|
| Маршрутизация по конфигурации | Services и Routes; декларативное описание в YAML/JSON | Конфигурация `server`, `location`, `upstream`, `proxy_pass` | Routers, Services и Middlewares; правила по имени хоста и пути |
| Проверка аутентификационной информации | Плагины JWT, Key Authentication, Basic Authentication | Basic Authentication; проверка токенов через внешний сервис с `auth_request` | BasicAuth; делегирование проверки внешнему сервису через ForwardAuth |
| Проверка JWT | Штатный JWT-плагин проверяет подпись | В стандартной OSS-поставке целесообразно использовать внешний сервис проверки через `auth_request` | Можно организовать через внешний сервис с ForwardAuth; не следует смешивать возможности Proxy и коммерческого Hub |
| Терминация HTTPS | Поддерживается, сертификаты устанавливаются на шлюзе | Поддерживается средствами HTTP SSL | Поддерживается на HTTPS-router; доступны заданные сертификаты и ACME |
| Организация конфигурации | В том числе DB-less: единый декларативный файл без отдельной БД | Конфигурационные файлы | Динамическая конфигурация, в том числе правила маршрутизации и TLS |
| Особенности эксплуатации | Специализированный API Gateway с механизмом плагинов | Удобен как reverse proxy; расширенную аутентификацию нужно организовать отдельно | Удобен для динамической маршрутизации; сложную аутентификацию можно вынести во внешний сервис |
| Соответствие требованиям | Соответствует | Соответствует, при необходимости с внешним сервисом аутентификации | Соответствует, при необходимости с внешним сервисом аутентификации |

Декларативная конфигурация Kong и проверка JWT описаны в его документации; для NGINX документирована проверка через подзапрос, а для Traefik — ForwardAuth и конфигурация HTTPS.

### Выбор: Kong Gateway OSS

Kong выбирается не потому, что NGINX или Traefik не подходят, а потому, что его модель ближе к поставленной задаче: централизованному управлению API и проверке учётных данных клиентов.

1. Маршрутизация описывается декларативно.  
   Services, Routes и плагины можно хранить в YAML/JSON. В DB-less-режиме отдельная база данных не требуется, что позволяет включить конфигурацию шлюза в Git и доставлять её через CI/CD. При загрузке декларативного файла Kong заменяет конфигурацию целиком.

2. Для проверки JWT не нужен отдельный самописный сервис.  
   JWT-плагин проверяет подпись токена и пропускает запрос к upstream только при успешной проверке. Проверку `exp` и `nbf` необходимо явно включить в конфигурации: одной проверки подписи недостаточно для контроля срока действия токена.

3. Решение разделяет функции шлюза и приложения.  
   Предлагается проверять учётные данные на входе, а бизнес-авторизацию — например, право пользователя изменить конкретный заказ — оставлять в микросервисе. Это не позволит ошибочно считать любой запрос с валидным токеном разрешённым.


### Предлагаемая организация

```text
                         ┌── Kong Gateway №1 ──┐
Клиент ── HTTPS ── L4 LB ─┤                     ├── Микросервисы
                         └── Kong Gateway №2 ──┘
```

Для production предлагаю:

- Развернуть минимум два экземпляра Kong на разных узлах.
- Перед ними разместить L4-балансировщик, чтобы HTTPS завершался именно на Kong.
- Хранить маршруты и настройки плагинов в Git, а ключи и сертификаты — отдельно от репозитория.
- В DB-less-режиме доставлять одинаковую конфигурацию на все экземпляры: отдельная БД не требуется, но синхронизацию конфигурации должен обеспечивать процесс развёртывания.
- Закрыть административный интерфейс от внешней сети.
- Не разрешать клиентам обращаться к микросервисам в обход Gateway.
- При требованиях к шифрованию внутреннего трафика использовать HTTPS и между Gateway и сервисами.


## Задача 2. Брокер сообщений

### Сравнение решений

В таблице NATS рассматривается именно с JetStream: у JetStream есть настраиваемые дисковое хранение, репликация и подтверждения. Сравнивать его с Core NATS без учёта этих возможностей было бы некорректно.

| Критерий | RabbitMQ с quorum queues | Apache Kafka | NATS JetStream |
|---|---|---|---|
| Основной сценарий | Очереди задач, команды и обмен сообщениями между сервисами | Потоки событий, хранение журнала и повторное чтение | Обмен сообщениями и сохраняемые потоки на основе subjects |
| Кластеризация и надёжность | Quorum queues реплицируются с использованием Raft | Репликация партиций между брокерами | Настраиваемое число реплик потока |
| Хранение на диске | Сообщения quorum queues сохраняются на диске | Дисковый журнал сообщений | Дисковое хранение при выборе `File`; существует и режим `Memory` |
| Производительность: качественная оценка | Подходит для оперативной доставки отдельных сообщений; результат зависит от подтверждений, репликации и дисков | Ориентирован на высокую пропускную способность потоковой обработки, в том числе благодаря партиционированию | Подходит для обмена с низкими задержками; сохранение и репликация добавляют накладные расходы |
| Форматы сообщений | JSON, XML, Protobuf и другие форматы в теле сообщения | Произвольные сериализованные данные, например JSON, Avro, Protobuf | Произвольная полезная нагрузка, например JSON или Protobuf |
| Разделение прав | Virtual hosts; права `configure`, `write`, `read` на ресурсы | ACL на ресурсы, включая topics и consumer groups | Права публикации и подписки на subjects |
| Модель получения | Потребитель подтверждает обработку сообщения; возможна повторная доставка | Потребитель отслеживает позицию чтения; данные сохраняются согласно retention | Поведение определяется настройками stream и consumer: подтверждениями, retention и повторной доставкой |
| Эксплуатация: оценка для этой задачи | Умеренная сложность; нужно контролировать очереди, диски и состояние реплик | Более высокая сложность: партиции, реплики, retention, балансировка нагрузки | Относительно компактная система, но необходимо понимать subjects, streams, consumers и настройки хранения |
| Предпочтительная область применения | Надёжная доставка бизнес-задач между микросервисами | Большие потоки событий и многократная независимая обработка | Системы, где важны модель subjects и компактность инфраструктуры |


### Выбор: RabbitMQ с quorum queues

Для поставленных требований предлагаю RabbitMQ: его модель хорошо соответствует доставке задач и бизнес-событий от одного микросервиса к другому.

#### 1. Надёжность обеспечивается репликацией очередей

Самого объединения узлов RabbitMQ в кластер недостаточно: очередь может находиться на одном узле. Поэтому для критичных сообщений нужно явно использовать quorum queues — реплицируемые очереди на основе Raft. 

Предлагаемая конфигурация:

- Три узла RabbitMQ на разных физических узлах или в независимых зонах.
- По три реплики каждой критичной quorum queue.
- Постоянные диски для данных каждого узла.

Для очереди с тремя репликами доступность сохраняется при отказе одной реплики, пока две оставшиеся могут образовать большинство. Потерю двух узлов такая конфигурация не выдерживает.

#### 2. Сообщения сохраняются на диске

Для quorum queues сохранение сообщений на диске предусмотрено самим типом очереди — независимо от признака persistent у отдельного сообщения.

Однако дискового хранения недостаточно для надёжного взаимодействия приложений. Необходимо использовать:

- Publisher confirms — производитель получает подтверждение принятия сообщения брокером.
- Manual consumer acknowledgements — потребитель подтверждает сообщение только после успешного завершения обработки. 


#### 3. Доступ можно разделить между сервисами

RabbitMQ позволяет разграничивать окружения или группы приложений через virtual hosts, а внутри них задавать отдельные права на настройку, публикацию и чтение ресурсов. 

### Предлагаемая организация

```text
orders-service
      │
      │ publish + publisher confirms
      ▼
RabbitMQ: exchange orders.events
      ├── quorum queue billing.orders ──────► billing-service
      └── quorum queue notifications.orders ► notifications-service
                                                   │
                                              manual ACK
```


## Итоговое обоснование

| Компонент | Выбранное решение | Причина выбора |
|---|---|---|
| API Gateway | Kong Gateway OSS | Маршрутизация через Services/Routes, проверка JWT и возможность декларативной работы без отдельной БД. |
| Брокер сообщений | RabbitMQ с quorum queues | Репликация очередей, сохранение сообщений на диске, подтверждения доставки и разграничение прав на ресурсы. |
