# Предложение: платформа на базе Kubernetes

**Основа решения — Kubernetes** (управляемый, например VK Cloud Kubernetes, или свой дистрибутив вроде Deckhouse) **плюс набор дополнений**, которые закрывают требования, не входящие в «голый» Kubernetes: маршрутизация извне, хранение секретов, автомасштабирование узлов.

## Состав решения

| Слой | Компонент | Роль |
|---|---|---|
| Оркестрация | **Kubernetes** + containerd | Запуск контейнеров, самовосстановление, планирование по узлам |
| Сеть | **Cilium** (CNI) | Сеть между подами, NetworkPolicy, балансировка через eBPF |
| Обнаружение сервисов | **Service + CoreDNS** (встроены) | DNS-имена вида `orders.shop.svc.cluster.local` |
| Входящий трафик | **Gateway API** (Envoy Gateway / Cilium Gateway) | L7-маршрутизация извне: хосты, пути, TLS |
| Масштабирование | **HPA, KEDA, Cluster Autoscaler** | Автомасштабирование подов и узлов |
| Конфигурация | **ConfigMap / Secret** | Передача переменных среды в контейнеры |
| Секреты | **Vault / OpenBao + External Secrets Operator** | Централизованное безопасное хранение и ротация |
| Доставка | Helm + **Argo CD** | Деплой из Git |
| Наблюдаемость | Prometheus, Grafana, Loki | Метрики (нужны и для автоскейла), логи |

## Как закрываются требования

### 1. Поддержка контейнеров
Kubernetes работает с containerd и запускает любые образы. Минимальная единица — **Pod** (один или несколько контейнеров с общей сетью). Приложения описываются через **Deployment** или **StatefulSet**.

### 2. Обнаружение сервисов и маршрутизация
- **Внутри кластера.** У подов меняются IP, поэтому перед ними ставится **Service**: это виртуальный IP и DNS-имя, которое CoreDNS резолвит. Сервис `orders` обращается к `http://payments:8080`, а Kubernetes балансирует запрос на живые поды. Запрос получают только поды, прошедшие `readinessProbe`.
- **Снаружи.** **Gateway API** — современная замена Ingress. Через него задаётся правило вида «`api.example.com/orders` → сервис `orders`», плюс TLS.
- **Между сервисами (L7).** При необходимости добавляется service mesh: шифрование mTLS, ретраи, таймауты и трассировка без изменений в коде.

### 3. Горизонтальное масштабирование
Достаточно увеличить `replicas` в Deployment (`kubectl scale deploy orders --replicas=5`). Service сам добавит новые поды в балансировку. Узлы добавляются в node group без остановки кластера.

### 4. Автоматическое масштабирование (три уровня)
- **HPA** меняет число подов по CPU/памяти (через metrics-server) или по своим метрикам из Prometheus (RPS, латентность).
- **KEDA** масштабирует по событиям (длина очереди Kafka/RabbitMQ) и умеет уменьшать число подов до нуля.
- **Cluster Autoscaler** добавляет узлы, когда подам не хватает места, и убирает лишние.

### 5. Разделение внешних и внутренних ресурсов
Разделение строится на нескольких уровнях:
- **Тип Service.** `ClusterIP` (по умолчанию) доступен только внутри кластера. Наружу трафик идёт только через Gateway (за ним один `LoadBalancer`), а не через публикацию каждого сервиса.
- **Два шлюза:** внешний (публичный IP, WAF, rate limit) и внутренний (балансировщик во внутренней сети).
- **NetworkPolicy** (Cilium): в каждом namespace по умолчанию запрещён весь трафик (default-deny), разрешено только явно нужное. 
- **Namespaces + RBAC + ResourceQuota** для логической изоляции команд и окружений.

### 6. Конфигурация через переменные среды и секреты
- Несекретные настройки хранятся в **ConfigMap**, чувствительные — в **Secret**. Оба подключаются в контейнер как `env`/`envFrom` (принцип 12-factor).
- Обычный Secret в etcd лишь закодирован в base64, а не зашифрован. Поэтому добавляем:
  - **шифрование etcd at rest** через KMS;
  - **RBAC**: доступ на чтение секретов только у сервисного аккаунта;
  - **Vault/OpenBao** как источник истины. Здесь хранятся пароли, ключи и сертификаты, поддерживаются аудит доступа, ротация и динамические креды к БД. **External Secrets Operator** синхронизирует их в Kubernetes Secret.
  - В Git секреты не попадают.

## Обоснование выбора

1. **Все требования закрываются штатными механизмами.
2. **Kubernetes — индустриальный стандарт.** У него крупнейшая экосистема (Helm-чарты, операторы для БД и очередей).
3. **Декларативность и GitOps.** Состояние системы описано в Git, изменения проходят ревью, откат делается одним коммитом, окружения dev/stage/prod воспроизводимы.
4. **Самовосстановление и бесшовные релизы.** Упавший под перезапускается, а rolling update обходится без простоя.
5. **Переносимость.** Есть managed-варианты у российских облаков (VK Cloud, Yandex Cloud) и on-prem-дистрибутивы (Deckhouse, в том числе сертифицированные версии), поэтому нет привязки к одному провайдеру.
6. **Рекомендуется managed Kubernetes.** Control plane, обновления и etcd обслуживает провайдер, а команда занимается приложениями.
